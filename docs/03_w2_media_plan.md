# W2：把 TF 卡里的照片变成窗口画面

> 现状：**W1 固件不读卡**。墙面现在的 4 个窗口是程序化生成的图案（彩条/棋盘/渐变/导航），
> TF 引脚根本没接进 `wall_node_*`。所以卡插在板上目前是"插着但不工作"。
> 本文说明素材要求和 W2 的两种接法。

## 1. 卡的要求（这些不满足，FPGA 一定读不到）

| 项 | 要求 | 说明 |
|---|---|---|
| 文件系统 | **FAT32** | `fat32_scan` 只认 FAT32；exFAT / NTFS **不行**。64 GB 以上的卡 Windows 默认格 exFAT，要手动选 FAT32（或用 32 GB 及以下的卡） |
| 目录 | **根目录** | 只扫根目录，不递归子目录 |
| 文件名 | **8.3 大写**，扩展名 `.BMP` | 如 `CAM1.BMP`；`监控1.BMP`、`cam 1.bmp` 都不认 |
| 格式 | **24 位非压缩 BMP（BITMAPINFOHEADER）** | 见 `bmp_parser.v`：magic `BM`、`biBitCount=24`、`biCompression=0` |
| 尺寸 | 建议 **640×480** | 与帧缓存 1:1；其它尺寸需要缩放（W2 只做最近邻） |
| 行对齐 | 4 字节 | 640×3 = 1920 已对齐，无需 padding |

`wall/media/CAM1.BMP` … `CAM4.BMP` 已按上述要求生成（各 921,654 字节 = 54 + 640×480×3）。

## 2. 素材怎么来的

本机访问不了外网，所以这 4 张是 `tools/make_camera_bmps.py` 用 PIL 画的"仿真摄像头画面"：
停车场 / 走廊 / 机房 / 夜景城市，右下角带 `REC OK` 和红色录制点，左下角带点位和假时间戳。
看起来像真的监控画面，答辩时也能自圆其说（"视频源与显示节点解耦，本次用图库素材演示"）。

要换成真实照片：把 jpg/png 放到 `wall/media/src/`，我写一个转换脚本统一转成 640×480 24-bit BMP。

## 3. W2 两种接法（需要选一个）

### 方案 A：整帧合成到帧缓存（复用校赛已验证通路）

```
TF → FAT32 → BMP 解码 → SDRAM 图库（4 张 640×480）
                              ↓
      窗口表 + 合成器（把桌面/窗口/边框画进 back buffer）
                              ↓
              SDRAM 双缓冲 → line_prefetcher → HDMI 扫描输出
```

- 复用：`m2_slave_tf_hdmi_top` 的 TF/FAT32/BMP/SDRAM 写通路、`p1_sdram_hdmi_pipeline` 的扫描输出
- 新增：一个"合成器"，按窗口表把 4 张图 + 桌面背景画进 back buffer
- 代价：**要动 150 MHz 域**，P1-05A 的 hold 余量只有 3 ps，需要重新收敛 STA
- 优点：与原始方案 3 的设计图一致，答辩讲得清；窗口缩放、任意叠放都好做

### 方案 B：窗口行缓冲（不动 150 MHz 读出）

```
TF → BMP → SDRAM 图库
                  ↓ 每行消隐期预取
        每个窗口一条行缓冲（640×24 bit BRAM）
                  ↓
   现有组合逻辑合成器：窗口区域内从行缓冲取像素，其余仍是程序化图案
```

- 复用：现有 W1 渲染器（一行都不用改桌面/边框/HUD）
- 新增：每窗口行预取状态机（消隐期 6.4 µs 内取 640 个 32-bit word，150 MHz 足够）
- 代价：4 个窗口各一条 640×24 行缓冲 ≈ 61 kbit BRAM；窗口缩放比较受限
- 优点：**不碰帧缓存的 hold 余量**，风险低；扫描输出路径完全不变

### 我的建议

先做 **B**：它把"照片进窗口"这件事用最小改动做完，而且不破坏已经收敛的 150 MHz 读出路径。
B 跑通后，如果答辩需要"任意尺寸窗口 + 平滑缩放"，再升级到 A。

## 4. 落地顺序（B）

1. `sd_spi` + `fat32_scan` + `bmp_parser` + `bmp_pixel_stream` 接进节点（复用校赛代码）
2. 上电时把根目录里的 `CAM1..CAM4.BMP` 依次写进 SDRAM 的 4 个图库区（19.6K LUT 里够放 4×1.2 MB）
3. 每窗口一条行缓冲 + 预取状态机（消隐期工作）
4. 合成器：窗口内容坐标 `(cx,cy)` → 图库地址 `img_base[src] + (cy*2 + 0)*640 + (cx*2)`（2:1 下采样）
5. 状态串口加"图库已加载 / 卡错误"字段，方便不看屏判断

## 6. 方案 B 的地址与带宽预算（2026-10-28 定稿）

### 6.1 SDRAM 地址分配（2^21 = 2,097,152 字）

| 区 | 起始字地址 | 长度 | 用途 |
|---|---:|---:|---|
| 图库 0 | `0x000000` | 307,200 | CAM1 640×480 |
| 图库 1 | `0x04B000` | 307,200 | CAM2 |
| 图库 2 | `0x096000` | 307,200 | CAM3 |
| 图库 3 | `0x0E1000` | 307,200 | CAM4 |
| 自检区 | `0x1E0000` | 1,024 | `wall_sdram_test`（**必须挪到这里**，现在还在 0x001000，会踩图库 0） |

### 6.2 每行要取多少数

窗口内容区宽 316，源图 640 宽 → 2:1 最近邻 ⇒ 每行每窗口取 **320 个源像素**
（取偶数地址 `base + 2*src_row*640 + 2*i`）。

但只取**本屏可见部分**：

| 节点 | 可见窗口 | 每行取数量 |
|---|---|---:|
| A | 0,1,2（窗口 2 只有左 120 px） | ≈ 320+320+120 = 760 |
| B | 2（右 220 px）、3 | ≈ 220+320 = 540 |

### 6.3 带宽账（关键）

- 一行 800 个像素时钟 @25 MHz = **32 µs**
- 每行最多 ~760 个读请求（4-word 组缓存的命中率约 50%，实际约 1 字 / 3.5 拍 @150 MHz）
  → 760 × 3.5 ≈ **2660 拍 ≈ 17.7 µs** < 32 µs ✅ 占 55%
- 剩余带宽留给将来的图库加载（写）与刷新

结论：**能跑，但不宽裕**。所以：
1. 取数要按"可见裁剪后的列数"取，不能整行 640 取
2. 窗口内容按 2:1 取，不做任意比例缩放（任意比例需要除法/步进器，另算）
3. 每窗口行缓冲 320×24 bit × 4 = 30.7 kbit，BRAM 放得下

### 6.4 模块划分

```
pixel 25MHz                                   sdr 150MHz
─────────────────────────────────────────────────────────────
行起始(de 上升) → 每个可见窗口算
   {win_id, img_base, src_row, n_cols}
        │  描述符（toggle 握手，4 组）
        ▼
                            wall_img_fetch：按描述符读 SDRAM
                            → 写 wall_img_buf 对应窗口的行缓冲
        ▲                        │
        │  lb_data[23:0]         │
   wall_img_buf（4×320×24，简单双口）
        │
   场景：窗口内容区取 lb_data[cx]
```

- 描述符用 toggle 握手（4 个窗口各一对寄存器 + toggle），不需要 FIFO
- 取数在 150 MHz 域连续跑，不挤在消隐期（消隐只有 6.4 µs，来不及）
- 行缓冲读地址 `cx = x - gx`（内容区偏移）由场景给出

### 6.5 仿真与验收

1. `tb_img_fetch`：用行为级 SDRAM 模型，喂任意"图片"，比对行缓冲内容与期望值
2. 真板：先把图库用**图案生成器**填（棋盘/渐变/彩条），窗口显示取自行缓冲的内容 →
   验证取数通路；再接 TF 加载真实照片
3. 验收指标：窗口内容不撕裂、跨接缝内容连续、每行取数不超时（可用 status 里的
   行内最大取数拍数监测）
