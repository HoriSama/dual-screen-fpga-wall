## C9 —— 四张 1:1 相册（2026-10-31 16:5x，已上板）

**目标**：相册（SW4）从"只能看 CAM1"改成 **CAM1..CAM4 四张、KEY3/KEY4 切页、每张都是
1:1 像素**；B 跟着切；桌面缩略图/轮播/亮度对比度/UI/静音/拔线降级全都不变。
代价：MUSIC.WAV 从 1.25 M 字缩到 619,520 字（≈26 s → ≈12.9 s）。

**地址表"正好用满"**（2,097,152 字 = 整个 2M×32）：

| 区域 | 地址 | 大小 |
|---|---|---|
| MUSIC.WAV | 0 … 619,519 | 619,520 |
| HI0 (CAM1) | 619,520 … 926,719 | 307,200 |
| HI1 (CAM2) | 926,720 … 1,233,919 | 307,200 |
| HI2 (CAM3) | 1,233,920 … 1,541,119 | 307,200 |
| HI3 (CAM4) | 1,541,120 … 1,848,319 | 307,200 |
| 四张缩略图 | 1,848,320 … 2,097,151 | 4 × 62,208 |

`619,520 + 4×307,200 + 4×62,208 = 2,097,152`，没有空隙。缩略图**整体上移**但
`PIC_STRIDE = 62,208` 没动（只有一个基址变了）。代码里 307,200 用
`2^18+2^15+2^13+2^12` 的移位加法，**不引入乘法器**（C5 的教训：25 MHz 那条链上一个乘法器
就翻负）。

**页码放哪**：窗口记录 `[60:59]`（C9 前是 `rsv` 全 0）。这是**故意的**——记录宽度、STATE 帧
格式、B 的跟随逻辑一个字节都不用改：表每帧整份广播，B 下一帧就看到新页码。
`wall_input` 写记录时高 6 位恒 0，所以只有相册时序器能设这两位。见 `docs/01_spec.md` §3.1。

**切页**：`wall_input` 在 album 分支里做 KEY4/KEY3 的边沿检测，出两个单周期脉冲
`alb_next`/`alb_prev`（这一支**不写表**，表归 `wall_album_seq`）。时序器只在 `S_ALBUM`
（淡入做完）里响应，**只重写 slot 0 一条记录**，页码 0→1→2→3→0 回绕；进出相册时页码保持。
不要淡入淡出：相册是 1:1，行缓冲每行都换源行，所以新页最迟在**下一行**（≈32 µs）就整屏换成新的。

**加载器**（`wall_tf_load`）：
- `hi_addr = HI_BASE + cid*307200 + y*640 + x`，四张都写；
- 去掉 `cid==0` 才读到文件末尾的保护 → **这是最容易漏的一条**：不去掉的话第 2..4 张的 1:1
  拷贝在 144 个采样行之后就 `bank_done`，拷贝只有上半部分；
- `bank_ok[cid]` 的含义因此变成"第 cid 张的缩略图 **和** 1:1 拷贝都写完"，所以 A 的
  `hi_ready` 直接取 `&tf_bank_ok[3:0]`（四张都在 SDRAM 里才允许翻页）。

**链路**：区域 5 → 8（0..3 缩略图、4..7 四份 1:1），一轮 **83,712 块**。
`got`（接收器）和 `cur_blk`（推送器）**都必须加宽到 17 bit** —— 16 bit 在 65,535 处绕回，
B 的 `b_hi_ready` 永远等不到（交接文档 §6 预警过 `got`，`cur_blk` 要自己想到）。
一个块占 12.5 µs，`allow` 在 y=4..472 都为真，所以一轮实际约 **1 s**（不是文档里那句
"一块占 16.7 ms 的一帧"），上电约 2 s 后 B 的四份拷贝就齐了。

**取图源**：`wall_pic_prefetch` 多输出 4×2 bit 页码（`nxt_idx`），`wall_pic_line` 在请求扫描时
把它和 burst 基址**一起锁存**，150 MHz 侧仍然只做 4 选 1（地址运算全部留在 25 MHz 侧）。

**状态帧 byte 19**（原来恒 0 的 picture-RAM 自检）改成 `{5'b0, 页码[1:0], hi_ready}`，
串口就能看出"相册为什么是黑的"和"现在是第几页"（`tools/read_status.ps1` 已跟着改）。

**这一轮踩到的坑**：
1. **`cur_blk` 也要 17 bit**（交接文档只提了 `got`）。`CUR_LAST = 83,711` 塞不进 15 bit。
2. **`tb_carousel.v` 是 C3 之前的陈旧 TB**：端口位宽早就不匹配（`nxt_rows` 32/36、
   `rd_win` 2/3、`rd_col` 9/10），读回来的是 X，所以它"一直在 FAIL"而没人发现它不在回归里。
   把位宽修好后它仍然 FAIL —— 一开始我判断"它假设 `car_cyc` 会旋转**取图源**，而 RTL 里
   取图源一直是窗口号，所以是 TB 错了"。**这个判断是错的**：C2 年代 `wall_pic_line` 里确实有
   `req_pic_r[...] <= sch + car_cyc`，是 **C3 的重写把它丢了**。所以 TB 是对的、RTL 是错的，
   见下面「C9-R1」。教训：**先查历史版本再给"陈旧 TB"定罪**——
   `build/release/*/rtl/` 里每一版 RTL 都在，`grep car_cyc` 五秒钟就能证伪。
3. **`tb_tf_load` 的卷原来是 640×480 / 384×288 / 192×144 混着**。C9 的验收口径是"四张 1:1
   逐字比对"，所以四张底图都改成 640×480，而且**像素各不相同**（否则把 CAM2 拷进 CAM3 的区
   也看不出来）。卷因此涨到 7,258 扇区（3.7 MB），`NSEC` 8192、`TIMEOUT` 9 M 周期。

**回归**：16 个 TB 全 PASS。`tb_tf_load` 逐字比对 `110592/110592` 抽样 + **`1228800/1228800`
四份 1:1**（真·逐字，不是抽查）；`tb_pic_line` 新增页 2（第 9 行）和页 3（第 300 行）
两段 640 字 burst 的地址逐字比对；`tb_album_page`（新）覆盖切页回绕、只在 `S_ALBUM` 响应、
页码跨进出保持、只写 slot 0。

**时序 / 面积**（`build/td_A|B/final_timing.rpt` 的 Clock Summary）：

| | LUT | reg | BRAM | 25 MHz | 150 MHz | 其他 | 最薄 hold |
|---|---|---|---|---|---|---|---|
| A | 13083 / 19600 (66.75%) | 8111 | 31 / 64 | **+0.265** | **+0.518** | 50 MHz +11.379 / 125 MHz +4.493 | HWNS **+0.004**（150 MHz 域） |
| B | 8512 / 19600 (43.43%) | 6082 | 31 / 64 | **+0.504** | **+0.247** | 6.25 MHz +149.88 / 50 MHz +11.839 / 125 MHz +5.402 | HWNS +0.011 |

对比 C8：A 25 MHz +0.888 → +0.265（LUT +306：17 bit 计数器、8 区解码、页码 mux），
150 MHz +0.130 → +0.518；B 25 MHz +0.284 → +0.504，150 MHz +0.582 → +0.247。**0 违例**，
但 A 的 150 MHz 域 hold 只剩 **+0.004 ns**——下次重建先看这一行。

## C9-R1 —— VIEW 模式 KEY3 单步 / 自动轮播"看不出换图"（C3 起的回归，2026-10-31 17:2x 修）

**操作员报告**：VIEW 模式关掉自动轮播以后，按 KEY3（手动切下一张）没反应。
（顺带说明：**自动轮播其实也早就不换图了**，只是每 256 帧还会淡一下，不容易一眼看出。）

**根因**：`wall_pic_line` 取图源的地址里丢了轮播相位。
- C2 年代的代码（`build/release/20261031_031026_B/rtl/wall_pic_line.v`）：

  ```verilog
  req_pic_r[{sch, 1'b0} +: 2]   <= sch + car_cyc;   // mod 4
  ...
  rd_addr  <= pic_base(wr_pic) + ...
  ```
- C3 重写（`20261031_113240_A` 起）把它换成了
  `req_base[sch] <= req_addr({hi_l[sch], sch}, rows...)` —— **`car_cyc` 只剩失效逻辑
  `car_chg`，不再进地址**。

于是从 C3 到 C9：`car_cyc` 照常前进、淡入淡出照常、亮度表照常跟着相位转（`scene` 里
`pic_idx = id + car_cyc`），但**每个窗口始终取同一张缩略图**。KEY3 按下去只有 `car_step`
脉冲 → 相位 +1 → 画面不变，看起来就是"没反应"。

**修法**（`wall_pic_line`）：请求扫描开始时把相位锁进 `car_l`，取图源用
`sch + car_l`（mod 4）：

```verilog
if (prime | line_tick) car_l <= car_cyc;              // 一次扫描相位不变
req_base[sch] <= req_addr(hi_l[sch], idx_l[..], sch[1:0] + car_l, rows_l[..]);
```

- 只有**缩略图**路径用 `sch + car_l`；`frameless`（相册）窗口仍然用记录 `[60:59]` 的页码，
  所以 **C9 的切页不受轮播相位影响**（B 的相位镜像晚一帧也不会让相册跳页）；
- 相位锁在扫描起点，4 个窗口的请求永远用同一个相位，相位不会在扫描中途变；
- `car_chg` 的失效逻辑原样保留（它清 `filled`、把 `last_row` 置全 1，逼下一拍重取）。

**为什么以前没测出来**：`tb_carousel` 正是测这个的，但它从 C3 起就没进回归；
而且它的端口位宽（`nxt_rows`、`rd_win`、`rd_col`）在 C3 之后就不匹配了，读回来全是 X。
这一轮把位宽修好 → 它立刻 FAIL → 顺着它查到上面的根因。**修完 `TB_CAROUSEL PASS`，
重新纳入回归**。

**顺带修掉的**：`wall_scene` 的亮度索引是 `id + car_cyc`，以前画面不转但亮度在转，
所以"调亮度调到的是另一张图"；现在两者一致了。

**C9-R2 重建（2026-10-31 16:5x）**：A 25 MHz **+0.220** / 150 MHz **+0.140**（LUT 13112、reg 8099、HWNS +0.011）；B 25 MHz **+0.404** / 150 MHz **+0.578**（LUT 8642、reg 6084、HWNS +0.003）。**0 违例**。回归 **23 个 TB 全 PASS**（含新增 `tb_prefetch_node`）；两片已重烧（`FLASH_OK`），A `phase=6 / bank_ok=000f / hi_ready=1`、B `link=1 sync=1 / hi_ready=1`。**板上 `late`（byte 11）静止时 A=11、B=0** —— A 那 11 次基本是每帧开头 buffer 还是空的（`prime` 后头几行），不是稳态饥饿。

**时序 / 面积（C9-R1 重建，2026-10-31 16:4x）**：
A 25 MHz **+0.914** / 150 MHz **+0.276**（LUT 12858、reg 8042、BRAM 31、DSP 14、HWNS +0.014）；
B 25 MHz **+0.192** / 150 MHz **+0.339**（LUT 8523、reg 6084、HWNS **+0.003**）。**0 违例**。
按说只多了"一个 2 bit 加法 + 一个 2 bit 锁存"，但 TD 的布局对网表变化很敏感：
A 的 25 MHz 从 +0.265 涨到 +0.914，B 的 25 MHz 却从 +0.504 掉到 +0.192。
**下次重建先看 B 的 25 MHz（+0.192）和 hold（+0.003）这两行。**

**板级**：两片已重烧（`probe_flash.ps1 -Flash`，cable 0 = A / cable 1 = B，两次 `FLASH_OK`）。
A：`phase=6 / err=0 / found=000f / bank_ok=000f / hi_ready=1`；B：`link=1 sync=1 / hi_ready=1`。

## C9-R2 —— 相册切页加渐变 + 上下移动时的抖动（2026-10-31 17:4x）

操作员两个反馈：
1. 大屏模式切图（KEY3/KEY4 换 CAM）能不能也走渐变；
2. **上下移动任何一张图**时，靠后的那两张图（他看到的是"图片3 在 A 屏的部分"和"图片4 从
   `PIC 3 LOCKED` 那行到中心偏下"）会抖动。

### R2-1 切页渐变（照做）

`wall_album_seq` 里加了一位 `paging`：在 `S_ALBUM` 收到 `nxt/prv` 时**不**立刻改表，而是走
和进出相册**同一条** `S_FADE_O → S_SWAP → S_SETTLE → S_FADE_I`：
- 淡出 16 帧 → 全黑时**只写 slot 0**（`paging` 让 S_SWAP 只写一条就跳出，槽 1..3 保持"blank"）
  → 等 2 帧 commit → 淡入 16 帧，合计 ≈34 帧 ≈ **567 ms**；
- 页码在**全黑那一刻**才 `idx <= idx_pend`，所以淡出期间画面仍是旧图；
- 淡入淡出期间按键**不响应**（时序器不在 `S_ALBUM`），和进出相册的手感一致；
- 页码跨进出保持、切页只动 slot 0 —— 这两条 `tb_album_page` 现在都断言了
  （写表时 `level==0`、`wr_slot0` 恰好 +1、`wr_other` 不变、`level` 回到 16）。

### R2-2 上下移动时的抖动：不是"移动"的问题，是**读口预算**

先算账。一行 31.7 µs ≈ 4758 个 150 MHz 拍。一张缩略图一行是 **192 字**的 burst，
而 `wall_pic_line` 的 150 MHz burst 循环是"发一个地址 → 等 rvalid → 再发下一个"，
每字要 4~6 拍（缓存适配器每 4 字有 1 次 miss），所以**一个 burst ≈ 1000~1200 拍 ≈ 7~8 µs**。
四个窗口都要换行时 = **4 × 7.5 µs ≈ 30 µs ≈ 一行的 95%**。
再加上音乐读、B 板收到的块写、仲裁开销，**一行的预算就爆了** → 排在扫描顺序最后的两个窗口
（`sch = 2,3`）拿不到新行，`wall_pic_line` 就按设计"保持上一行多显示一行"。

为什么**只在上下移动时**看得出来：静止时被保持的那一行和正确的那一行在画面上几乎看不出差别
（最近邻放样本来就会重复行）；一移动，`gy` 每帧变一次，被保持的行就落在不同位置，
**看起来就是那一块在抖**。左右移动不改变取图行，所以不抖。

这也解释了"为什么偏偏是第 3、4 张"：请求扫描固定按 0→1→2→3 发，先发的两张总能拿到。

**这一轮做的事（去掉无谓的 burst）**：`wall_pic_prefetch` 加了 `NODE_X0/NODE_W`，
`nxt_valid` 多了"这个窗口是否碰得到本节点的半屏"这一条 —— 以前**每片板都取它根本画不到的那些
窗口的行**（4 个窗口分散在 1280 宽的世界里，典型布局每片只画 2~3 个）。现在：
A 半屏只取 `gx` 落在 0..639 的窗口，B 只取 640..1279 的窗口，跨缝的窗口两边都取。
`tb_prefetch_node` 钉住了边界算术（正好**结束**在 640 的窗口算 A 的，正好**开始**在 640 的算 B 的，
跨缝的两边都要，相册那个整幅窗口两边都要）。
这一条把 burst 数从"每片 4 个"降到"每片实际画的个数"，典型布局省掉 25~50%。

**还留了一个量尺**：`wall_pic_line` 新增 `late_cnt` —— 上一帧里"上一条行时发起的 burst 到这一条行
还没回来"的次数（0 = 读口跟得上）。装载完成后它出现在**状态帧 byte 11**
（`tools/read_status.ps1` 会打印 `late=`），饱和值 255。**上板时这样用**：
静止时读一次、按住 KEY3/KEY4 上下移动时读一次 —— 如果移动时它明显大于 0，
说明 burst 还是超一行，那就得再动结构（每窗口 3~4 个行 bank 的环形缓冲，把"峰值 4 个 burst/
行、平均 2.96"削平）；如果恒为 0，抖动就来自别的地方（比如最近邻放样本身的重复行）。

⚠ 顺便记一笔：**C4 时代踩过同一类的坑**（`wall_top` 里那段注释）——
pusher 和行缓冲抢读口时"每行第一列…整块抖动"，当时的修法是把 pusher 限制在场消隐。
这次剩下的是行缓冲自己四个 burst 的竞争，性质一样：**行缓冲必须在一行之内填完**。

## C9-R3 —— 只剩「图三在 A 屏的那条」还在抖（2026-10-31 18:3x，已上板）

**操作员反馈（C9-R2 之后）**：图四不抖了，**图三在 A 屏的那条还在抖**，而且"它自己动、或者别的图动"时都看得出来，位置在屏幕上半部分。

**先加探针，再动手**。上一轮只报"本帧 starving 的行数"，一个每帧都被覆盖的数字，人来不及看。这一轮改成：

- `wall_pic_line` 多出 `late_msk[3:0]`：本帧哪个窗口挨饿（按窗口，不是按行）；
- `wall_top` 攒成 **4 秒（240 帧）一个纪元的最大值 + 掩码**，纪元结束锁存；
- 状态帧：**byte 11** = 纪元内最差那一帧的行数，**byte 19 bits[6:3]** = 挨饿窗口掩码（bit3..bit0 = w3..w0）。`tools/read_status.ps1` 会打印 `starved-mask=0100 (w3..w0)` 和 `linebuf: worst frame / 4 s = 13`。

**测出来的数据（改之前那一刻）**：

| 板 | worst frame / 4 s | starved-mask | 解释 |
|---|---|---|---|
| A | **13** | **0100** | 只有 **w2（图三）** 挨饿。A 要取 3 个窗口（w0、w1、跨缝的 w2），而 150 MHz 侧的取数顺序是 **w0 > w1 > w2**，w2 永远排最后 → 三个窗口同时换行时它拿不到 |
| B | 0 | 0000 | B 只取 2 个窗口（w2、w3）→ 有余量。**这就是"图四好了、图三没好"的真正原因** |

**修法**：`wall_pic_prefetch` 多出一组 `nxt_c1` —— **每个窗口在本节点最多能看到第几列**，`wall_pic_line` 用它当 burst 的最后一列（以前硬编码 191/639）。

- 只有"右边界被本节点切掉"的窗口会被截短（实际就是**跨缝那个**）：`c1 = min(full, (NODE_X1 - gx) + 5)`；完全在本半屏的窗口 `gxroom >= w` → 保持整行；
- **为什么 `+5` 一定是安全上界**：源列 `sx = (2*px*zst)>>16`，只要 `zst <= 32768`（最多一个源列对一个绘制像素）就有 `sx <= px`，而本节点能画的像素数不超过 `NODE_X1 - gx`，所以 `gxroom + 5` 足够（留 5 列给舍入/边界）；`zst > 32768`（窗口被放大到 1:1 以上）时**不截短**，退回整行；`frameless`（相册）走 `px*zst>>16`，倍率天然 ≤ 1，同样是安全上界；
- **零乘法器**：只有加法/比较，不占 DSP。

**效果（A 板每行字数）**：改之前 `192 + 192 + 192 = 576`；改之后 `192 + 192 + 45 = 429`（**−26%**，跨缝那个 burst 从 192 字砍到 45 字，−77%）。按"一字约 6 拍"折算，A 的读口占用从 ~97% 降到 ~72%。

**验证**：`tb_prefetch_node` 新增断言 —— A 半屏最后一列是 `w0=191 / w1=191 / w2=45 / w3=5`，B 半屏两个窗口都是 191（B 的权利边界是世界边界，不是接缝）；`tb_pic_line` / `tb_album` 同步驱动 `nxt_c1`。回归 **23/23 PASS**。

**时序 / 面积**：A 25 MHz **+0.153** / 150 MHz **+0.304**（LUT 13370、reg 8216）；B 25 MHz **+0.242** / 150 MHz **+0.127**（LUT 8993、reg 6184）。**0 违例**。

> 这几轮的数字漂得很厉害（同一份 150 MHz 域，A 在 +0.025 ↔ +0.304 之间跳），TD 的布局对网表变化极其敏感 —— **每次重建都要重新看 STA，不能沿用上次的余量**。

**板级**：两片已重烧。静止状态连采 3 次：**两片都是 `starved-mask=0000`、`worst frame / 4 s = 0`**（改之前 A 是 `0100` / `13`）。待操作员按住上下键、并移动别的图，确认"图三那条"还抖不抖。

## C5 —— 进出相册的淡出/淡入（2026-10-31 13:40）

**为什么是“淡到黑”而不是叠化**：这套渲染器没有帧缓存，每个像素是 `f(x,y,窗口表)`
现算的，没有“上一帧”可以拿去和新帧混合。黑是渲染器自己能产生的颜色，所以
`淡出 → 换表 → 淡入` 是唯一不需要 2× 合成器的做法。

**时序**（`wall_album_seq`，`FADE_FRAMES=16`）：

```
16 帧淡出（level 16→0，267 ms）→ 4 个时钟换表（全黑，看不见）→ 等 2 帧
（stage→snap→cur 追平）→ 16 帧淡入（0→16，267 ms）= 533 ms
```

和 `wall_carousel` 换图的节奏一致（它也是 16 帧淡出/16 帧淡入），所以两种转场手感相同。

| 要点 | 做法 |
|---|---|
| 谁被淡 | `wall_scene` 末尾的**整幅合成**：桌面网格、边框、标题、照片、HUD 一起淡 |
| 增益编码 | `level[4:0]`，0 = 全黑，**16 = 精确直通**（`(c*16)>>4 == c`），所以逐像素 TB 全部保持 `tlevel=16` 不用改期望值 |
| 乘法大小 | 8×**5**（`c*level>>4`）。一开始写成 8×9（`c * {level,4'b0000} >> 8`）——**Node A 的 25 MHz 域直接掉到 -0.263 ns，A 还布不通**（`RUN-8102`）。换 8×5 后 A 是 +1.641 ns |
| 乘法放哪 | **必须**放在 `rgb_r` 之后（组合尾巴），不能放进 `rgb_c → rgb_r` 那一级：那条 `x → 窗口求值 → z 选择 → 内容/HUD` 的链只剩 +0.24 ns，任何加法都会翻负 |
| B 跟着淡 | `level` 通过 STATE 帧 **byte 4 bits[6:2]** 广播（原本 byte 4 只有 `car_auto`/`adj` 用了 bit0/1）；B 用它驱动同一个 dimmer，否则 A 黑了 B 还是亮的，然后突然切 |
| 换表时机 | `tb_album_tbl` 会断言：**表只在 `level==0` 时被写**、淡出正好 16 帧、结束后 `level` 回到 16 |

回归：`tb_scene` / `tb_img` / `tb_pipe_eq` / `tb_hud_dump` / `tb_album` 全部保持逐像素一致
（它们把 `tlevel` 钉在 16）；`tb_album_tbl` 新增淡入淡出断言。

**踩到的两个坑（都记在代码注释里了）**：

1. 把乘法放进输出寄存器前面 → 25 MHz 域 -0.263 ns，A 布线失败。时钟余量只有 +0.24 ns 的域里，
   **一个乘法器都不能加在关键链上**。
2. 8×9 那次即使时序过了，也让 A 的 LUT 逼近上限、路由 congested（`PHY-8023` / `RUN-8102`）。
   `c * level >> 4` 把三个砍掉约 60%。

## C8 —— 接缝上「每行第一列」低一行（2026-10-31 15:2x，已上板）

**现象（操作员实测）**：B 半屏**只有最靠接缝的那一列**比 A 低一行，其余列都正常；
桌面网格、边框、HUD 在接缝处完全连续。

**先排除的**：不是光栅相位/genlock（那样网格线也会歪）。所以原计划的「共享像素时钟」方案
**不需要做** —— 硬件、排线、PLL 都不用动。

**根因**：场景输出是打了一拍的，所以**每行第一个可见像素是在最后一个消隐时钟里合成**出来的；
行缓冲的读出又比它再深一拍，于是那一列的取样地址是**在 `de` 上升沿之前 3 拍**给出的。
而行缓冲的换 bank 原来发生在 `de_c` 的上升沿 —— 晚了 3 拍，那一列读到的是**上一行**。
A 板这一列是 world x=0（墙最左，看不见），B 板这一列是 **world x=640，正好接缝上**。

**诊断过程**（值得记的是方法）：先按"整行掉队"假设给 B 的预取行 +1，
操作员回报"最边上那一列对上了，右边反而全都高了一点" —— 一句话就把
"整行掉队"和"只有第一列"区分开，直接指向取样时刻而不是数据内容。

**修法**：
1. `wall_raster` 新增 `pre_de`：`hc + 3 == HBLANK`（活跃行内），即首像素前 3 拍；
2. `wall_top` 的 `line_tick` 改由 `pre_de` 驱动（换 bank + 请求下一行都提前 3 拍），删掉原来的 `de_c && !de_d`；
3. 顺手把 `wall_pic_prefetch` 的 `y_target` 打一拍：它只在行起点被采样，延一拍无害，
   却把 `y_c` 的一大条扇出支路摘掉了 —— 见下面的时序。

**时序**（这次的两个负余量都是布局噪声，靠上面第 3 条一起解决的）：

| | 改之前（C7） | 只加 `pre_de`（未打拍） | 最终（`y_target` 打拍） |
|---|---|---|---|
| A 25 MHz | +0.215 | +0.289 | **+0.888** |
| A 150 MHz | +0.261 | **−0.010** | **+0.130** |
| B 25 MHz | +0.360 | **−0.112** | **+0.284** |
| B 150 MHz | +0.733 | +0.681 | **+0.582** |

`y_target` 打拍前的负路径是 `u_pic_prefetch/y_target[2]` → `u_scene/rgb_c`（B，25 MHz）和
`u_sdram_adapter/mem_rdata_reg` → `u_sdram_test/failed`（A，150 MHz）：前者被那一拍摘掉，
后者跟着布局一起变好了。

**教训**：`de_c && !de_d` 这种"行起点"信号，在**有输出寄存器**的渲染器里天然晚；
任何"行起点"的动作（换 bank、取下一行、清计数）都要按**首像素前 N 拍**来算。

## C7 —— SW4 和 SW1+SW2+SW3 互换（2026-10-31 14:1x）

操作员要求：**SW4 上拨 = 全屏（相册）**，**SW1+SW2+SW3 同时上拨 = 亮度/对比度**。
原来是反的（SW4 = 调整，三个一起上 = 相册）。

改法只在 `wall_input` 的解码，`wall_album_seq` 一个字没动（它只认 `album` 这个电平）：

| SW1 | SW2 | SW3 | SW4 | 模式 | 按键 |
|---|---|---|---|---|---|
| 0 | x | x | x | VIEW | KEY4 轮播自动 / KEY3 单步 / KEY2 UI / KEY1 静音 |
| 1 | x | x | **1** | **全屏相册**（SW4 最高优先） | 全部失效（表归时序器） |
| 1 | **1** | **1** | 0 | **亮度/对比度** | KEY4/3 = 亮度 ±，KEY2/1 = 对比度 ±，长按一对 = 复位 0x80 |
| 1 | 1 | 0 | 0 | MOVE（已确认） | 上/下/左/右 |
| 1 | 0 | 1 | 0 | ZOOM（已确认） | 放大/缩小/快放/快缩 |
| 1 | 0 | 0 | 0 | 基础层 | 选图/确认/置顶/置底 |

两个细节：

- `adj_mode` 用的是**真实开关脚**（`sw_lvl[1] && sw_lvl[2]`），不是 `FORCE_DIRS` 覆盖后的 `sw2`，
  所以 autodrag 演示 build 不会因为一根被强制的 SW2 掉进调整层；
- `wall_hud` 的字幕跟着新解码走：`m_move` 现在要求 **SW3 下拨**（只有 SW2 上）、`m_zoom` 要求 SW2 下拨、
  `m_adj` 直接用广播过来的 `adj_on`（`mode_sw` 里没有 SW4，B 板只能靠这个），
  ADJUST 那行的 ON/OFF 也改成 `m_select | m_adj`，否则锁定窗口时字幕会显示 `ADJUST OFF` 而实际正在调。

回归：14 个 TB 全 PASS（`tb_drag` / `tb_mute` 也一并跑了，它们直接实例化 `wall_input`）。
A：12777 LUT，25 MHz **+0.215**、150 MHz **+0.261**；B：8525 LUT，+0.360 / +0.733。

```
byte 0 : {5'b0, region[2:0]}    0..3 缩略图，4..7 四份 1:1 拷贝（C9：原来只有 4）

byte 3..34 : 16 个字（低字节先）
```

模块参数（push 与 recv 必须一致，C9 的现值）：`BLK_PER_BANK=1728`、`BLK_HI=19200`、

## C3 —— 相册模式

### 记录里的 FRAMELESS 位

记录 `[63:58]` 是保留位，用 **bit 58** 做 `frameless`（原计划写的是 `[55:54]`，
但那两位其实是 `id[1:0]`，会打架）。`wall_input` 每次写记录时高 6 位固定填 0，
所以只有相册时序器能把它置起来。

`frameless = 1` 的含义（`wall_window_eval` / `wall_scene` / `wall_pic_prefetch`）：

- **命中判定恒真**：无边框、无标题，窗口就是整个 1280×480 世界
  （`w` 字段只有 10 位、最大 1023，装不下 1280，所以干脆不参与几何）；
- 内容区 = 1280×480，采样源是 **HI_BASE 的 640×480 拷贝**；
- `wall_zoom_calc` 用 **640/480 的分子**而不是 96/72：`step = 65536`、
  `dw = 640`、`dh = 480`。

### 进入 / 退出

- **SW1 + SW2 + SW3 全上拨 = 相册**（`wall_input` 的解码顺序按计划改成
  `SW4 → SW2&SW3 → SW2 → SW3`，但四种模式现在**互斥**，不需要优先级链：
  album 要 SW2 和 SW3 同时上、move 排除 SW3、zoom 排除 SW2、adjust 排除这两者）。
- `wall_album_seq` 在 `album` 上升沿**快照**当前 4 条记录（取 `cur_tbl`，
  即屏幕上那张表），然后 4 个时钟写完全表：slot 0 = 相册记录，slot 1..3 = `w=h=0`
  （不抹掉它们的话，prefetch 会在每一行多抓 3 条缩略图行，读口不够）。
- `album` 落下后 4 个时钟把快照写回。
- **不动 `sel`**：相册窗口 id=0、HUD 关闭，`sel` 不影响画面；不动它反而省掉了
  "stage 比 cur 快两帧、还原 sel 会错一拍"的问题。
- 节点 B 没有开关、没有时序器：它靠 STATE 帧里的窗口表（每帧 32 字节全表）
  自然跟到同一张表——这也是整件事只改表、不改画面通路的好处。

### 相册记录

```
gx=0 gy=0  w=1023 h=480  src=0  z=3(最上)  owner=A  flags=0  id=0  frameless=1
```
`w/h` 只为了让状态帧读到个合理值，几何上被忽略。

### 数据通路改动

| 模块 | 改动 |
|---|---|
| `wall_pic_prefetch` | `nxt_rows` 8→**9 位**（0..479）；新增 `nxt_hi[3:0]`；frameless 行号 = 活动行；`h==0` 的空白记录不再算可见 |
| `wall_pic_line` | 行缓存 `LINE` 192→**640**（数组 8192×16，BRAM 20→31）；`rd_win` 2→**3 位**（高位 = frameless）、`rd_col` 9→**10 位**；请求里带 **burst 起始地址 + 最后一列**，乘法/移位搬到 25 MHz 域；`pic_base` 扩到 5 项 |
| `wall_scene` | frameless 几何（全屏、无 chrome）；hi 采样**不乘 2**；`lb_rd_win/col` 位宽；`pic_valid[4]` = 全分辨率就绪；HUD / 电平条在相册模式全部关掉 |
| `wall_zoom_calc` | frameless 用 640/480 分子；分频器 `num/rem` 24→**26 位**（`640<<16` 装不进 24 位） |
| `wall_top` | `hi_ready`（A = `tf_bank_ok[0]`，B = 收满 26,112 块）与 `pic_ready` 分开；抓图闸门按窗口选；相册期间 `fade_gain` 强制 255（不然轮播包络会把静照调成呼吸） |
| `wall_album_seq` | **新模块**，可单独仿真 |

### 关键设计取舍

**150 MHz 域不许加逻辑**。原计划是让 burst 侧用 `row_q` 算 `base + row*192/640`，
那是一条新的乘加路径；150 MHz 域历来只有 +0.1~+0.5 ns。改成：**25 MHz 侧算好
burst 起始地址和最后一列**，150 MHz 侧只剩"两个 4 选 1 mux + 一个 10 位比较"。
实测 150 MHz 域 SWNS **A +0.162 / B +0.266 ns**，和改之前一样。

**hi 采样不乘 2**。缩略图路径是 `sx = (2*px * step) >> 16`，那个 2 是
"96 → 192"的换算；640/96 不是整数，所以换不成"乘 6.67"。解法是让
`wall_zoom_calc` 直接吐 640/480 基准的 step，scene 里 hi 分支就不乘。

## 已完成：C2a（2026-10-31 03:3x，`tb_tf_load` PASS）

> **C9 已把这张表整个换掉**（WAV 619,520 / HI0..HI3 四份 / 缩略图 1,848,320 起），
> 下面这一节保留的是 C2a 当时的样子，仅作历史记录。

**加载器现在多产出一份 640×480 的 1:1 拷贝**，放在 SDRAM 新区域：

| 区域 | 地址 | 大小 | 用途 |
|---|---|---|---|
| MUSIC.WAV | 0 … **1,249,999** | 1.25 M 字 | 上限 `WAV_CAP`，超了只停写不停读 |
| **全分辨率图（CAM1）** | **1,300,000 … 1,607,199** | **640×480 = 307,200 字** | 相册模式 1:1 显示 |
| 桌面四张采样图 | 1,700,000 … 1,948,831 | 4 × 62,208 | 现有窗口/桌面通路 |
| SDRAM 自检 | 1,966,080 … | 1,024 | 不变 |

实现要点：
- 写口现在是**两个生产者共用一个端口**（`hold_*` = 192×144 采样通路，优先级高；`hi_*` = 全分辨率通路）；
  源像素间隔约 100 个时钟，仲裁器**不需要停顿**；
- 全分辨率拷贝只做 **picture 0（CAM1）**，`px < 640 && hi_y < 480` 才写，因此 640×480 的源是 1:1；
- `src_row` 记录源行号，`hi_y = bottom_up ? img_h-1-src_row : src_row`，地址 `HI_BASE + y*640 + x`；
- **picture 0 的循环要多走一会儿**：采样通路在 144 个保留行后就 `bank_done`，而全分辨率拷贝还需要剩下的源行，
  所以 `cid==0` 时一直读到 `src_row+1 >= img_h` 再退出（否则 640×480 的图会丢掉最上面 2 行）。
  → 也正因为如此，`tf_bank_ok[0]` 正好在**全分辨率拷贝写完**那一刻才置位，可以直接当 `hi_ready` 用；
- `tb_tf_load` 的 CAM1 改成了 **640×480**（就是卡里那张图的尺寸），并且新增 `expected_hi.hex`
  （307,200 字）做逐字比对。
